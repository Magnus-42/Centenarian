# 04 · 验证与测试

> 本篇围绕 `RTL/Top/subsys_test_top.v` 设计：双网口经光缆交叉对接、自发自收，是最接近实际使用的验证环境。早期单层验证顶层（`cmac_test_top` 等）不在本篇范围。
>
> 本文各场景的**结果数据来自 `Scripts/hw_ila_vio.tcl` 的一次完整自动验证**（`hw_run scall`），原始记录存放在 [`results/`](Results/) 目录，例如 [`Results/scall_2026-10-14.txt`](Results/scall_2026-10-14.txt)。

## 总体框架

```text
QSFP 光缆交叉：A.TX ──→ B.RX      B.TX ──→ A.RX

subsys_test_top
 ├─ eth_subsys_top（被测子系统，2 口，配置见 02 的示例二）
 ├─ 23 台打流机（A 侧 11 台 + B 侧 12 台，每台对应一路发送使能）
 ├─ VIO：23 位使能，逐台控制打流机启停
 └─ ILA：挂各打流机的统计计数【使用 (* mark_debug = "true" *) 标记】
```

每台打流机的能力：

- 发送固定长度帧（1024 字节 = 16 拍），内容按所在协议层组帧；
- 接收端**逐拍校验**数据内容，帧头用对齐标志锁定；
- 每 1 秒输出一批统计：`rx_pkt_per_s`（包速率）、`rx_bw_bytes_per_s`（字节吞吐）、`rx_error_cnt`（内容错误）、`rx_len_err_cnt`（包长异常）；
- 接收端永不反压 —— 打流机挂在接收通道上，同时起到排水作用，这也是「未匹配」通道必须有消费者。

**交叉原则**：A 侧使能的流量经光缆到达交换机，经过交换机转到 B 口，由**挂在 B 口通道上的那台打流机**统计（反之亦然）。看统计时认准接收通道所在的口，而不是发送侧。

## 上板步骤

1. 建工程、综合、实现并生成 bitstream（见 README「快速开始」）；
2. 两个 QSFP 口经外部光缆**交叉对接**（A.TX → B.RX，B.TX → A.RX）；
3. 在 Hardware Manager 里**下载 bitstream 并刷新调试核（ltx）** —— 刷新后 VIO 与 ILA 才会枚举出来；
4. 在 Tcl Console 里加载验证脚本：`source ./Scripts/hw_ila_vio.tcl`；
5. 之后按需用 `hw_run scN` 跑场景验证，或 `hw_run on/off ...` 手工逐位控制。

### 脚本化验证

加载（GUI，Tcl Console）：

```tcl
source ./Scripts/hw_ila_vio.tcl
```

脚本会连上 `hw_server`、枚举调试核、打印 23 位使能映射（含每位的收端打流机名）与可用命令，随后逐条调用：

| 命令                | 对应场景         | 动作与判定依据                                                         |
| ----------------- | ------------ | --------------------------------------------------------------- |
| `hw_run sc1`      | 场景 1 · 连通性   | 逐位单开，核对「该位 → 对应收端打流机」有包，且 `rx_error_cnt` / `rx_len_err_cnt` 为 0 |
| `hw_run sc2`      | 场景 2 · 单通道线速 | 双向同开，读两台打流机的 `rx_bw_bytes_per_s` 并换算线速，≥ 99 Gbps 判通过            |
| `hw_run sc3`      | 场景 3 · 严格优先级 | 全部打开后自高向低逐路关闭：当前最高优先通道应独占线速，其余应被饿死（≈0）；最后核对全关基线归零               |
| `hw_run sc4`      | 场景 4 · 未匹配通道 | 四个兜底探测位逐侧单开，核对报文落在对端「未匹配」档且错误计数为 0                              |
| `hw_run scall`    | ①~④ 全跑       | 依次执行并输出总判定表                                                     |

| `hw_run refresh`  | —            | 重新枚举调试核（**重新下载 bit 后使用**，同时清理脚本内部缓存）                            |
| `hw_run vionames` | —            | 诊断：打印 VIO 探针真实名称、可用属性、当前输出值                                     |
| `hw_run iladiag`  | —            | 诊断：打印 ILA 触发属性、采集上传结果、取值方式、探针原始值与解析值                            |
| `hw_run csvpeek`  | —            | 诊断：打印本次采集导出的 CSV 前两行（核对列名与数值格式）                                 |

参数与示例：



### 手工控制 VIO 与读取 ILA

需要自己控制节奏时，可直接用底层命令（参数写法与 `-tclargs` 一致）：

```tcl
hw_run on en_a_udp monitor 10 rx_bw    # 开 A 口 UDP，连续采集 10 次只看吞吐类探针
hw_run on en_a_udp en_b_udp csv cap.csv  # 多条命令连写；csv 额外导出原始波形
hw_run set 0                           # 全部关闭（也支持 set 0x5 这样的位图整体设置）
```

- 探针即打流机内部 `(* mark_debug *)` 的统计寄存器（`rx_pkt_per_s` / `rx_bw_bytes_per_s` / `rx_error_cnt` / `rx_len_err_cnt` / `debug_rx_lock`），均为 1 秒锁存的慢变量，任意时刻触发采集读到的都是最近一次锁存值，因此切换使能后需等待 ≥ 2 秒再读；

## 吞吐换算成线速

打流机每秒导出一次 `rx_bw_bytes_per_s`（字节 / 秒，按 **64 字节 / 拍**累计，即统计的是总线占用量）。把它换算成以太网线速时，**额外长度按打流机所在层次取不同值**：

```text
线速(bps) = rx_bw_bytes_per_s × 8 × (L + 额外长度) / L
```

| 打流机所在层次                                                                                  | 额外长度    | 说明                                                      |
| ---------------------------------------------------------------------------------------- | ------- | ------------------------------------------------------- |
| MAC（`mac_88b5` / `mac_88cc` / `fb_mac`）                                                  | **+24** | 打流机自己组完整 MAC 帧；24 = 前导码与起始符 8 + FCS 4 + 帧间隔 12          |
| IPv4 / IPv6（`icmp` / `ospf` / `ipv4_06` / `ip6icmp` / `ip6ospf` / `fb_ipv4` / `fb_ipv6`） | **+38** | 打流机发的是完整 IP 包，DUT 再加 14 字节以太网首部：24 + 14                 |
| UDP（`udp` / `fb_udp`）                                                                    | **+58** | 打流机发的是 UDP 载荷，DUT 再加 20 字节 IPv4 首部与 8 字节 UDP 首部：38 + 20 |

- `L` = 单帧的 AXIS 字节数（不含 FCS，CMAC 已配置为收发各插 / 剥 FCS）；本环境为 1024 字节；
- 脚本按上表自动选择额外长度，场景输出里每行都会给出换算后的线速（Gbps）。

## 验证场景

> 时钟主频：200MHz

### 场景 1 · 通道连通性（逐路开启）

方法：VIO 一次只开一位，逐路确认「发送使能 → 对应收端打流机」的映射。

预期：收端 `rx_pkt_per_s > 0`，且 `rx_error_cnt` / `rx_len_err_cnt` 为 0。

> **错误计数判定规则**：除 **MAC 未匹配档 `fb_mac`** 外，各通道的内容错误与包长错误计数都必须为 0。`fb_mac` 是 MAC 层的兜底档，交换机的其他报文会自然落进该档，与打流机的 1024 字节模板不一致，因此它的错误计数不参与判定。

**结果**（200 MHz 用户时钟，`hw_run sc1`）：**23 路全部 PASS**。

| 通道分组                     | 使能（A/B 两侧）                               | 包速率 `rx_pkt_per_s`      | 换算线速          | err / len_err     |
| ------------------------ | ---------------------------------------- | ----------------------- | ------------- | ----------------- |
| UDP                      | `en_a_udp` / `en_b_udp`                  | 11 552 854 ~ 11 552 858 | 100.0015 Gbps | 0 / 0             |
| IPv4（ICMP / OSPF / 0x06） | `en_[ab]_icmp` / `ospf` / `ipv4_06`      | 11 770 422 ~ 11 770 423 | 100.0015 Gbps | 0 / 0             |
| IPv6（ICMPv6 / OSPFv3）    | `en_[ab]_ip6icmp` / `ip6ospf`            | 11 770 422              | 100.0015 Gbps | 0 / 0             |
| MAC（0x88B5 / 0x88CC）     | `en_[ab]_mac_88b5` / `en_b_mac_88cc`     | 11 927 660 ~ 11 927 661 | 100.0015 Gbps | 0 / 0             |
| 未匹配探测（IPv4 / IPv6 / UDP） | `en_[ab]_fb_ipv4` / `fb_ipv6` / `fb_udp` | 11 552 854 ~ 11 770 431 | 100.0015 Gbps | 0 / 0             |
| 未匹配探测（MAC）               | `en_[ab]_fb_mac`                         | 11 927 662              | 100.0015 Gbps | 74 / 37、94 / 47 ※ |

> ※ `fb_mac` 的错误计数来自交换机上的其它帧（见上文判定规则），脚本会在该行注明，不参与判定。

**结论**：23 组「发送使能 → 收端打流机」映射全部正确；各通道换算线速均为 100.0015 Gbps；除 `fb_mac` 外错误计数全为 0。逐路完整数据见 [`Results/scall_2026-10-14.txt`](Results/scall_2026-10-14.txt)。

### 场景 2 · 单通道线速（双向满载）

方法：两侧同开同一协议的使能，双口同时满载发送。

预期：双向换算线速均达到 100 Gbps。实测（2026-10-10，400 MHz 用户时钟，1024 字节帧）：

| 通道         | 额外长度  | A→B 线速             | B→A 线速             | err / len_err |
| ---------- | ----- | ------------------ | ------------------ | ------------- |
| `udp`      | +58 B | 100.001506929 Gbps | 100.001509634 Gbps | 0 / 0         |
| `icmp`     | +38 B | 100.001505312 Gbps | 100.001506374 Gbps | 0 / 0         |
| `ospf`     | +38 B | 100.001509560 Gbps | 100.001508498 Gbps | 0 / 0         |
| `ipv4_06`  | +38 B | 100.001505312 Gbps | 100.001509029 Gbps | 0 / 0         |
| `mac_88b5` | +24 B | 100.001586328 Gbps | 100.001587376 Gbps | 0 / 0         |
| `ip6icmp`  | +38 B | 100.001586555 Gbps | 100.001587617 Gbps | 0 / 0         |
| `ip6ospf`  | +38 B | 100.001506905 Gbps | 100.001506905 Gbps | 0 / 0         |

**结论**：7 个通道双向同时满载，换算线速全部达到 **100.0015 Gbps**（门限 99.0 Gbps）、错误计数全 0 —— 即在 200 MHz 用户时钟下各层次均跑满 100G 线速（完整数据见 [`Results/scall_2026-10-14.txt`](Results/scall_2026-10-14.txt)）。

### 场景 3 · 严格优先级

方法：多路同时打开，高优先级通道满载时应独占线速；随后**自高向低逐路关闭**，

每一步都由当前优先级最高的通道接管满速。

通道优先级取自顶层 `RTL/Top/subsys_test_top.v` 的 `PRIO_*` 常量（数值越大越优先）：

| 通道                         | 优先级 (口A / 口B)   |
| -------------------------- | --------------- |
| ICMPv6（`ip6icmp`）          | 14 / 14         |
| OSPF（`ospf`）               | 13 / 13         |
| OSPFv3（`ip6ospf`）          | 13 / 12         |
| ICMPv4（`icmp`）             | 12 / 11         |
| UDP（`udp`）                 | 8 / 9           |
| IPv4 协议 0x06（`ipv4_06`）    | 7 / 6           |
| MAC 自定义 0x88B5（`mac_88b5`） | 6 / 5           |
| 兜底探测（`fb_*`）               | 2 / 2（最低，不抢业务流） |

场景 3 用其中的 5 个通道（`ospf` / `icmp` / `udp` / `mac_88b5` / `fb_ipv4`）做逐路关闭，预期顺序为**OSPF → ICMP → UDP → MAC 自定义 → IPv4 未匹配档**，最后全关基线归零：

| 步骤 | 打开的通道      | 独占线速的通道        |
| -- | ---------- | -------------- |
| 1  | 5 路全部      | OSPF           |
| 2  | 关 OSPF     | ICMP           |
| 3  | 再关 ICMP    | UDP            |
| 4  | 再关 UDP     | MAC 自定义 0x88B5 |
| 5  | 再关 MAC 自定义 | IPv4 未匹配档      |
| 6  | 全关         | —（基线归零）        |


**结果**：**6 步全部 PASS**，实测与上表的 `PRIO_*` 顺序完全一致。

| 步骤 | 打开的通道      | 实测独占线速                                        | 其余打开通道                   | 判定   |
| -- | ---------- | --------------------------------------------- | ------------------------ | ---- |
| 1  | 5 路全部      | `ospf` 100.001515401 / 100.001510091 Gbps     | 全部 0.000000000 Gbps（被饿死） | PASS |
| 2  | 关 OSPF     | `icmp` 100.001506905 / 100.001506905 Gbps     | 全部 ≈0                    | PASS |
| 3  | 再关 ICMP    | `udp` 100.001507470 / 100.001503142 Gbps      | 全部 ≈0                    | PASS |
| 4  | 再关 UDP     | `mac_88b5` 100.001587376 / 100.001588424 Gbps | `fb_ipv4` ≈0             | PASS |
| 5  | 再关 MAC 自定义 | `fb_ipv4` 100.001510091 / 100.001506374 Gbps  | —                        | PASS |
| 6  | 全关         | —（基线）                                         | 无残留                      | PASS |

**结论**：优先级顺序与顶层 `PRIO_*` 常量一致（OSPF 13 > ICMPv4 12/11 > UDP 8/9 > MAC-88B5 6/5 > 兜底探测 2）；每一步均由当前最高优先级通道独占 **100.0015 Gbps**，低优先级通道被完全饿死，全关后基线归零（完整数据见 [`Results/scall_2026-10-14.txt`](Results/scall_2026-10-14.txt)）。

### 场景 4 · 未匹配通道

方法：打开 `en_*fb_*` 探测位，发送规则表之外的类型 / 端口。

**结果**：**8 次探测全部 PASS**。
